# 需求评审

先分级，再决定流程重量。不要一上来写 FRS。

## 1. 分级

| 级别 | 判据 | 后续 |
|---|---|---|
| **S** | 文案、样式、单页面小改 | 跳过整套；把验收条件记到既有需求或改动说明 |
| **M** | 单个功能模块 / 单页面新增 | `FRS.json` + `README.md` + 原型页面；`FLOW.md` / `STATE.md` 按需 |
| **L** | 多模块联动 / 新核心概念 / 影响面广 | 全套 FRS；先定边界，再画原型 |

不确定时按高一级处理，并明确写出不确定点。

## 2. 评审输出

用下面的结构回复，不写成散段落：

```md
## 分级
M / L / S — 一句判据

## 要解决的问题
业务侧痛点，一条一句

## 范围
- 包含：
- 不包含：

## 用户任务
1. 谁，在什么场景，要完成什么

## 现状与 Delta
- 已有：
- 本次新增/修改：
- 需要保护的既有行为：

## 风险与待确认
- [ ] 问题 — 为什么重要 — 谁来确认
```

## 3. 边界

- 不把「实现方案」写成需求事实；研发未确认的契约放 `openQuestions`。
- 不根据原型示例数据推断业务规则；规则必须来自需求或界面文案。
- 用户没有确认范围前，不进入 L 级全套产出。
- 评审结论落到需求 `README.md`；跨需求决定才进 `docs/DECISIONS.md`。

## 4. 下一步

M / L 级进入 `.agent/skills/prd-author/SKILL.md`；S 级直接实现并补验收条件。
